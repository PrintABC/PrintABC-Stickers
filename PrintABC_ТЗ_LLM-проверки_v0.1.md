# ТЗ: LLM-проверки макета наклеек — v0.1

**Назначение:** дополнение к «ТЗ Автопроверка v0.1». Описывает участки конвейера, где языковая модель эффективнее детерминированного кода, и правила её применения.
**Стек:** Claude API (или Gemini API — интерфейс одинаковый), вызовы из того же Python-модуля. Температура 0, ответ строго JSON.

---

## Принцип разделения (главное правило всего ТЗ)

| Задача | Кому | Почему |
|---|---|---|
| Измерить (мм, dpi, pt, координаты) | КОД | Модель видит картинку без физического масштаба — измерения будет угадывать |
| Оценить как человек (читаемо? криво? уместно?) | LLM | Кодом это правила на тысячи строк с ложными срабатываниями |
| Написать текст клиенту | LLM | Формулировки — сильная сторона модели |

**Жёсткое ограничение:** ни одна цифра из ответа LLM не попадает в отчёт клиенту и не считается измерением. Цифры в отчёте — только из кода или из параметров заказа.

---

## Участки, где LLM эффективнее кода

### LLM-1 — Визуальная читаемость (замена CHECK 5, когда код бессилен)
**Когда:** текст переведён в кривые, макет растровый, или CHECK 5 дал PASS, но нужно подтверждение.
**Почему не код:** OCR + расчёт кегля по пикселям ловит размер, но не читаемость (тонкий шрифт 8 pt может быть хуже жирного 6 pt; низкий контраст текст/фон код не оценит).

**Вход:** PNG-рендер (150 dpi) + строка контекста: «Это наклейка {W}×{H} мм — размером примерно с {спичечный коробок / кредитку / ладонь}».
**Промт (ядро):**
```
Ты оцениваешь макет наклейки размером {W}×{H} мм ({бытовое сравнение}).
Представь её напечатанной в этом размере и лежащей на столе.
Ответь строго JSON:
{
 "smallest_text_readable": true/false,   // весь текст читается с расстояния 30 см
 "low_contrast_areas": true/false,       // текст сливается с фоном
 "thin_elements": true/false,            // линии/шрифты тоньше волоса — пропадут в печати
 "evidence": "какой именно текст/элемент проблемный, его расположение словами"
}
```
**Правило:** `false` по любому пункту → флаг `manual_review`; поле `evidence` используется владельцем для обводки на скриншоте, клиенту идёт переформулированным без цифр.

### LLM-2 — Артефакты ИИ-генерации
**Когда:** всегда (доля ЛЛМ-макетов растёт).
**Почему не код:** детекторов «кривых букв» и искажённых деталей кодом не существует в надёжном виде.

**Промт (ядро):**
```
Проверь, есть ли признаки генерации изображения нейросетью, которые испортят печать:
искажённые/выдуманные буквы, несуществующие символы, «оплывшие» детали, лишние пальцы/элементы,
нечитаемый псевдотекст. Ответ строго JSON:
{ "ai_artifacts": "none | suspected", "evidence": "что и где" }
```
**Правило:** `suspected` → отчёту клиенту разрешён отдельный блок «макет сгенерирован нейросетью — проверьте буквы под увеличением» + флаг `manual_review`.

### LLM-3 — Контент у края (замена CHECK 4 для растра и кривых)
**Когда:** файл растровый или в PDF нет живых объектов.
**Почему не код:** сегментация «важный элемент vs фон» кодом — отдельный ML-проект; модель делает это из коробки.

**Промт (ядро):**
```
Красной рамкой на изображении показана зона в 4 мм от края наклейки (наложить рамку КОДОМ до отправки).
Есть ли внутри рамки значимые элементы: буквы, логотип, лица, важные детали
(однотонный фон и текстуры — не считаются)?
{ "edge_content": "ok | suspected", "evidence": "что именно и с какой стороны" }
```
**Ключ:** рамку рисует код по известному масштабу — модель только смотрит внутрь. Так измерение остаётся за кодом.

### LLM-4 — Смысловая сверка макета и заказа
**Когда:** всегда; дешёвая страховка от дорогой ошибки.
**Почему не код:** сверить «в заказе написано наклейка на банку мёда, а в макете визитка стоматолога» кодом невозможно.

**Промт (ядро):**
```
Заказ: наклейка {W}×{H} мм, материал {material}, тираж {qty}. Язык клиента: {lang}.
Посмотри на макет и ответь:
{
 "looks_like_sticker": true/false,        // это похоже на макет наклейки, а не другой продукции
 "orientation_ok": true/false,            // ориентация файла соответствует пропорциям заказа
 "language_note": "none | mixed | wrong", // язык в макете радикально не совпадает с языком клиента
 "evidence": "..."
}
```
**Правило:** любые несовпадения → только `manual_review`, клиенту ничего автоматически не уходит (слишком много легитимных исключений).

### LLM-5 — Генератор отчёта клиенту (отдельный модуль)
**Когда:** после конвейера, вход — итоговый JSON проверок (код + LLM).
**Почему не код: ** шаблонные подстановки дают канцелярит; задача отчёта — «объяснить как человек» (Focus 1 Стратегии).

**Вход:** JSON вердиктов + язык клиента + утверждённая библиотека блоков (из шаблона v0.1) как few-shot примеры.
**Промт (ядро):**
```
Ты пишешь отчёт клиенту типографии от имени PrintABC на языке {lang}.
Данные проверки: {JSON}. Используй ТОЛЬКО перечисленные проблемы (максимум 3) и ТОЛЬКО цифры из JSON.
Каждая проблема по формуле: Что видим → Что будет при печати (результат в руках, не техтребование)
→ Что сделать (шаги в Canva ИЛИ готовый промт для нейросети) → Как проверить себя.
Запрещённые слова: блид, CMYK, dpi, кегль, вылет (говори «запас фона за краем»).
Примеры утверждённого тона: {блоки из библиотеки}.
Финал: «Исправьте и пришлите — проверим за 10 минут».
```
**Правило:** отчёт до отправки видит владелец (Этап 1–2); автоотправка — только после статистики ≥90% отчётов без правок.

## Общие правила для всех LLM-вызовов

1. **Формат ответа:** строго JSON. Парсинг в try/except; невалидный JSON → один повторный запрос → при повторной ошибке `manual_review`. Никогда не падать.
2. **Температура 0**, фиксированная версия модели в конфиге. Смена модели = прогон тестов приёмки заново.
3. **`evidence` обязателен:** ответ «suspected» без описания «что и где» считается невалидным — защита от галлюцинаций «на всякий случай».
4. **Каждый вызов логируется:** файл, промт-версия, ответ, финальное решение владельца. Этот лог — будущий датасет для оценки точности и порогов.
5. **Деградация:** API недоступен → конвейер завершает кодовые проверки, все LLM-пункты получают `manual_review`. Сервис не останавливается (Конституция: «починю в субботу вечером»).
6. **Стоимость:** 4 вызова на файл (LLM-1..4) + 1 на отчёт ≈ копейки против 250 ₪/ч ручной проверки. Оптимизация: LLM-1..4 объединяются в ОДИН вызов с общим JSON-ответом после отладки по отдельности.

## Тесты приёмки LLM-части

Тот же набор 15–20 реальных файлов с диагнозом владельца.
Метрики раздельно по каждой проверке:
- Пропуск реальной проблемы (критично, цель <10%)
- Ложная тревога (некритично: уходит в manual_review, цель <30%)
- LLM-5: доля отчётов, отправленных владельцем без правок (цель ≥70% на старте)
Асимметрия сознательная: лучше лишний раз посмотреть глазами, чем пропустить брак.
